# 学习自测：按用户问题估算的 Token，为什么和账单差很多？

> 📚 参考：[Token 的工程账本](/概念与原理/17ai/s_ai_34-token_budget) | [Token 与分词](/概念与原理/17ai/s_ai_8-tokenization) | [上下文窗口](/概念与原理/17ai/s_ai_21-context_window)

**场景**：老板问：这个月 AI 功能账单是预算的 3 倍，可用户平均只问了 200 字，怎么会烧这么多？

**考察点**：请求实际包含哪些 Token、多轮调用的重复上下文、工具结果与检索内容的占用、缓存的真实作用。

::: details

## 核心回答

**你估的是用户那句话，账单算的是整个请求 × 调用次数。**

| 被漏掉的输入 | 说明 |
| --- | --- |
| 系统 / 开发者指令 | 每个请求都带，通常比用户那句话长 |
| 对话历史 | 全量回放时，第 10 轮会把前 9 轮重发一遍 |
| 工具定义与返回 | 工具 schema 每轮都带；订单接口一次返回上百字段 |
| RAG 检索片段 | 命中越多、片段越长，占用越大 |
| 消息结构与特殊标记 | 每条消息都有角色标记等额外 Token |
| 多模态输入 | 图片按块计 Token，不是按文件数 |

再加上 Agent 的**多次调用**：一次用户请求可能触发 3～5 次模型调用，每次都重新带上历史与工具结果。

```text
用户 200 字 ≈ 几百 Token
× 每条消息的结构开销
× 历史累积
× 3～5 次调用
= 账单上看到的数
```

## 排查顺序

1. **先看 usage**：把每次调用的输入/输出用量记下来，**按任务汇总**，别只看单次。
2. **找最大头**：是历史太长、工具结果太肥，还是检索塞太多？
3. **分项优化**：
   - 历史：摘要 + 只保留相关轮次；
   - 工具：返回前裁剪字段（保留状态/权限/风险）；
   - RAG：提高相关性，减少条数与长度；
4. **验证**：优化后再按任务对比用量，而不是看单次请求。

## 两个常见误区

- **「开了提示词缓存就不占窗口」**：错。缓存影响计费，不改变这些内容仍占用上下文窗口。
- **「Token 减半，延迟减半」**：错。延迟还受 Prefill、并发、排队、网络影响。

## 面试回答要点

- 一句话：**账单 = 整个请求 × 调用次数，不是用户那句话**。
- 能列出至少 4 类被漏算的输入。
- 知道按任务汇总用量才找得到成本大头。
- 知道缓存省的是钱，不是窗口。
