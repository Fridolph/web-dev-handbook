# 学习自测：首字等很久、出字后又卡，怎么定位？

> 📚 参考：[一次生成的链路与推理性能](/概念与原理/17ai/s_ai_33-inference_pipeline) | [流式输出 Streaming](/概念与原理/17ai/s_ai_19-streaming) | [上下文窗口](/概念与原理/17ai/s_ai_21-context_window)

**场景**：AI 客服上线后被投诉「转圈 8 秒才出第一个字，出字后还一顿一顿的」。你手上只有一个接口和一张监控图，怎么定位？

**考察点**：Prefill / Decode 分工、TTFT 与输出速度、KV Cache、输入长度的代价、流式传输与模型生成的区分。

::: details

## 核心回答

先按**两段延迟**切开：首字慢 = Prefill 侧；出字后慢 = Decode 侧。两者优化手段完全不同。

| 现象 | 主要怀疑 | 怎么验证 |
| --- | --- | --- |
| 首字 8 秒 | 输入太长（历史消息、检索资料、工具结果全塞进去）、排队、模型冷启动、代理/网关缓冲 | 缩短输入对比 TTFT；换直连对比；看服务端排队耗时 |
| 出字后一顿一顿 | Decode 慢：并发打满、限流、长输出、KV Cache 压力大 | 看 Token/s 与并发曲线；降并发重测；缩短输出上限 |
| 首字快但全文很久 | 输出太长、Decode 正常但量太大 | 对比 Token/s 与输出长度 |
| 首字和出字都正常，页面还是卡 | 流式没真正生效（等全文再返回）、前端渲染/缓冲、网络分片 | 抓包看首包时间；临时改成非流式对比 |

## 排查顺序

1. **量出两个数**：TTFT 和 Token/s，别只看总耗时。
2. **先怀疑输入**：上下文越长 Prefill 越贵。历史是否全量带？检索片段是否太多？工具结果是否整段回填？
3. **再怀疑并发**：并发打满时 Decode 会明显变慢，KV Cache 显存也吃紧。
4. **验证流式真的生效**：首包是不是第一个 Token 就发出？有没有中间层把响应缓冲了？
5. **区分「文字出现」和「任务完成」**：Agent 场景里，等待可能发生在工具调用，而不是模型生成。

## 面试回答要点

- 说清 **Prefill → TTFT**、**Decode → Token/s** 的对应关系。
- 知道 KV Cache 省的是重复计算，代价是显存随长度和并发增长。
- 知道 SSE 只管传输，**一个 chunk ≠ 一个 Token**。
- 优化前先量化：先拿到 TTFT 和输出速度，再决定砍上下文、加并发上限还是换流式链路。
