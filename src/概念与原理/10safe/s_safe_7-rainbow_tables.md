# 彩虹表与离线密码破解

> 彩虹表针对的是密码哈希的离线猜测，并非 PostgreSQL 或 MySQL 专属漏洞。先假设攻击者已经取得密码验证数据，再讨论它有多难被利用。

## 一、拿到哈希后能做什么？

攻击者可以猜测候选密码，用相同算法、盐和参数计算，再与泄露值比较。匹配后就找到了能通过该验证的候选值，这是**猜测与验证，不是解密哈希**。

```text
候选密码 → 按存储规则计算 → 比较泄露的验证值 → 匹配则猜中
```

低熵密码容易被猜中，与算法能否抗碰撞不是同一问题。

| 方式 | 核心思路 |
| --- | --- |
| 字典攻击 | 优先尝试常见密码、泄露词库和变形组合 |
| 暴力枚举 | 按字符集与长度空间枚举 |
| 预计算查表 | 预先计算候选与结果，泄露后复用 |
| 彩虹表 | 用哈希链和不同归约函数，在存储与计算间折中 |

GPU 等硬件加速和字典猜测同样需要关注，不能把全部离线破解都称为彩虹表攻击。

## 二、彩虹表如何减少存储？

普通预计算表直接存大量“密码 → 哈希”映射，彩虹表则提前构造链，主要保存端点，查找时重建部分链：

```text
候选 p0 → H → h0 → R0 → p1 → H → h1 → R1 → p2 → … → 链终点
```

`H` 是哈希函数，`R` 将结果映射回候选密码空间，是归约函数，不是解密函数。经典彩虹表在不同链位置采用不同归约函数，降低部分链合并带来的重复；查询需要尝试定位、重建并验证，也不能覆盖所有密码。

能否复用预计算工作，取决于算法、参数、候选空间与盐是否一致。大量用户采用无盐快速哈希时，一批预计算结果可以复用，相同密码还会得到相同哈希，暴露关联。

## 三、随机盐为什么有效？

```text
验证值 = KDF(密码, 随机盐, 成本参数)
```

KDF 在这里指适合密码存储的派生或哈希方案。即使密码相同，盐不同通常也得到不同结果；针对一个盐的预计算不能直接复用于另一个盐，攻击者需要分别计算。

盐应由密码学安全随机数生成器产生，按库推荐长度使用，每次新建或更新密码时生成新的盐。**盐可以和验证值一起存储，不需要保密。**

用户名、手机号、固定字符串和时间戳可能重复或可预测，不宜代替独立随机盐。安全性不依赖隐藏盐，而在于降低跨用户复用计算的价值。

## 四、加盐为什么还不够？

盐公开后，攻击者仍然可以针对单个用户逐个猜测。`SHA256(salt + password)` 仍然很快，弱密码可能迅速被命中。因此需要组合：

- **独立随机盐**：降低预计算复用和相同密码关联。
- **有计算、内存成本的密码哈希**：如 Argon2id、scrypt，提高每次猜测成本。
- **难猜的密码与账号保护**：结合密码管理器、泄露密码检查及合适的 MFA 策略。

登录限流作用于在线请求，离线攻击发生在攻击者的设备上，通常不受接口限流约束。MFA 能降低密码泄露后的账号接管风险，但不改变哈希被离线猜测的速度。

## 五、Salt 与 Pepper

| 对比 | 随机盐（salt） | Pepper |
| --- | --- | --- |
| 保密性 | 不要求保密 | 必须保密 |
| 范围 | 每次密码存储独立生成 | 常由服务端管理，与多个记录关联 |
| 存放 | 与密码验证值一起保存 | 与密码数据库分离，例如受控密钥服务 |
| 作用 | 降低预计算复用 | 在仅数据库泄露时增加一道秘密依赖 |

Pepper 是可选的纵深防御，不能替代盐和 KDF。应使用经过审查的组合方式，并考虑轮换时旧记录如何验证、是否需要用户重设密码。

## 六、泄露后的处理边界

访问控制、备份保护与审计降低泄露概率；密码哈希降低泄露后的利用速度。不能仅凭“有盐”就判断安全，应结合算法、成本、密码强度和其他凭证暴露情况决定重置密码、撤销会话等措施。

应用用户密码与数据库连接认证也是不同层次：PostgreSQL 的 SCRAM-SHA-256 保护数据库连接认证流程，不代表业务用户表中的密码字段已被妥善保护。

## 七、一分钟复述

> 彩虹表是预计算攻击，用哈希链在存储与计算间折中，主要利用相同算法和参数下的计算结果复用。每个密码使用独立随机盐后，攻击者需要针对不同盐重新计算，通用预计算表的价值大幅降低。盐可以公开，但不能阻止逐个猜测，所以还要使用 Argon2id、scrypt 等有成本的密码哈希，并结合强密码和账号安全措施。
