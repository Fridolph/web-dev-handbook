# 从聊天机器人到 Agent：模型、应用与 Agent 的职责边界

## 概念

一次 AI 对话，是**模型 + 应用**共同完成的结果：模型只负责根据本次能看到的上下文生成内容；组织上下文、保存历史、检索资料、执行工具、校验权限、展示结果，全部发生在应用侧。

把这条边界想清楚，才能回答三个常见的混淆：

- 为什么补一句背景，回答就变了？——应用把背景放进了上下文。
- 为什么同一个模型换个产品体验不同？——应用层能力不同。
- 为什么模型说「已退款」不能信？——模型只生成文本，执行在业务系统。

> 这一篇不重复讲 Token、Embedding、RAG 的内部机制，只讲**各组件在一请求里的分工与边界**；具体原理见文末「和已有文章的关系」。

## 一次请求里发生了什么

```text
用户输入
   ↓
应用准备信息
├─ 对话历史
├─ 系统指令
├─ 检索到的资料
└─ 工具调用结果
   ↓
模型根据当前上下文生成内容（可能附带工具调用请求）
   ↓
应用执行工具、校验结果、展示，或继续下一轮
```

注意：不是每次请求都有检索或工具；模型与应用也可能来回多轮。这张图是简化流程，不是固定标准。

## 四层职责划分

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| **大语言模型** | 理解输入、生成内容、在支持时输出工具调用请求与参数 | 访问企业数据库、真正执行操作、保证事实一定正确 |
| **聊天产品** | 保存与展示历史、组装请求上下文、联网/读文件、记忆开关、账号与安全 | 决定模型内部如何生成 |
| **应用 / 业务代码** | 权限校验、规则判断（金额、期限、状态）、执行工具、校验结果、组装响应 | 生成自然语言解释 |
| **Agent 设计** | 围绕目标选择下一步、读取结果决定继续或结束 | 替代业务系统做最终业务决定 |

核心结论：**Agent 不是「把所有事交给模型」，而是「在可控边界内让模型参与决策」。**

## 七个类比的边界（重点）

类比能帮理解，但每个类比都有断点，工程上常踩的坑就藏在这里。

| 类比 | 成立的部分 | 边界（常被忽略） |
| --- | --- | --- |
| 模型 ≈ 内容处理服务 | 传入输入、拿到输出，可当成应用依赖的能力组件 | 也可以本地部署；输出不确定，不能当权威事实或业务决定 |
| 上下文 ≈ 函数入参 | 传不同参数，结果不同；背景、目标、约束越明确，输出越贴合 | 模型看不到整个聊天页面；长度有限需截取/总结；给了信息也不保证用对 |
| Token ≈ 积木块 | 模型处理的是编码后的序列，按 Token 计费和限长 | 一个 Token 不固定等于一个汉字或一个单词；精确统计要用目标模型的分词器 |
| 幻觉 ≈ 格式正确但数据错误的返回值 | 结构合法、读起来通顺，但内容无依据 | JSON 能解析 ≠ 字段真实；格式校验不能替代事实校验 |
| RAG ≈ 先查文档再回答 | 回答前补充外部依据，可附来源 | 手动贴一段资料只是给上下文，缺少「检索」这一环；RAG 不必须向量库；不等于重新训练模型 |
| Memory ≈ 持久化会话 + 用户配置 | 应用保存消息/偏好，下一轮再注入上下文 | 应用保存并注入，不等于模型每次聊天后修改了自身参数 |
| Tool Calling ≈ 前端调后端接口 | 模型发起请求，拿到真实数据再回答 | 模型只产出调用请求与参数，执行与权限在应用；查询与退款/支付风险不同；MCP 只是协议之一 |

## 串联案例：订单退货助手

用户问：「帮我看看订单 X308 能不能退货，能的话告诉我怎么申请。」一个合理的分工是：

```text
接收请求 → 查真实订单 → 查适用退货规则 → 用业务代码校验条件 → 必要时让模型解释 → 返回依据与申请方式
```

| 组件 | 在这条链路里的作用 |
| --- | --- |
| 上下文 | 问题、订单信息、相关规则等本次可参考的信息 |
| 工具调用 | 获取订单状态，或查询其他系统 |
| RAG | 从政策资料中检索适用条款 |
| 业务代码 | 校验订单状态、期限、权限等明确规则 |
| 大语言模型 | 理解请求、组织解释、参与下一步选择 |
| 聊天应用 | 管理界面、调用流程、历史记录与结果展示 |

**判断原则：确定性规则交给代码，模糊表达交给模型。** 金额、期限、权限这类有唯一答案的条件，用业务系统算；措辞、解释、下一步建议，可以交给模型组织。

## Node.js / NestJS 在链路中的位置

```text
前端页面
   ↓
NestJS 应用接口
   ├─ 身份与权限校验
   ├─ 查询数据库或业务服务
   ├─ 调用检索服务
   ├─ 调用模型
   └─ 组装并返回结果
```

对前端同学来说，先把 NestJS 当成「组织后端代码的框架」即可，不必把所有概念都类比成前端组件。Node.js / NestJS 只是可选技术栈，不是构建 Agent 的必要条件。

## 面试常问

- 模型、聊天产品、Agent 三者的边界分别在哪？为什么同一模型换个产品体验不同？
- 手动把资料贴进对话，和 RAG 的区别是什么？
- 工具调用时模型执行了操作吗？权限和校验由谁负责？
- 模型输出的 JSON 格式正确，就能直接写入业务库吗？
- 为什么说「Agent ≠ 所有事情都交给模型决定」？
