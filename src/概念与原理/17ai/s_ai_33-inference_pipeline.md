# 一次生成的链路与推理性能：Prefill、Decode、KV Cache

## 概念

一次回答 = 一串「预测下一个 Token」的循环。链路本身是固定的，但每一步的实现细节因模型而异。

工程上要关注两件事：

- **上下文**决定模型能不能答对（输入设计问题）
- **推理阶段**决定用户等多久（性能问题）

这篇把两者串起来，具体机制不重复展开，直接链到已有文章。

## 全链路

```text
上下文 → Tokenizer → Token ID → Embedding + 位置 → Transformer
      → Logits → 解码选 Token → 回填序列 → 继续循环 → 停止
```

| 环节 | 一句话 | 详见 |
| --- | --- | --- |
| Tokenizer | 文本切成 Token 并映射为 ID | [Token 与分词](./s_ai_8-tokenization) |
| Embedding | ID 转成向量，模型在训练中学到表示 | [Embedding](./s_ai_9-embedding) |
| 位置信息 | 让模型利用顺序与相对距离 | [Transformer 架构](./s_ai_7-transformer) |
| Attention | 按权重组合上下文不同位置的信息 | [Attention](./s_ai_10-attention) |
| Logits → Softmax | 候选 Token 的原始分数转概率 | [概率分布与 Softmax](./s_ai_17-probability_softmax) |
| 解码 | 贪心 / 采样，按参数挑下一个 Token | [Temperature 与采样策略](./s_ai_18-temperature) |

两个容易误解的点：

- **Token ID 是标识符**，编号大小不代表重要性。
- **注意力权重 ≠ 解释**。某个位置权重高，不能单独证明它就是最终答案的原因。

## 自回归的两个后果

1. **前文影响后文**：已生成的 Token 会进入后续上下文。
2. **错误会传播**：前面立错了假设，后文可能沿着错误方向展开；但也可能被后文修正。

停止条件通常是：生成结束标记（EOS）、达到输出长度上限、应用主动终止。

## 推理两阶段：Prefill 与 Decode

| 阶段 | 做什么 | 决定什么 |
| --- | --- | --- |
| **Prefill** | 一次性处理全部输入，算出第一个输出 Token 的分数，并建立缓存 | **TTFT**（首 Token 延迟）；输入越长通常越慢 |
| **Decode** | 基于已有内容逐个生成后续 Token | **输出速度**（Token/s） |

两个观察指标：

- **TTFT**：从发请求到收到第一个 Token 的时间。
- **输出速度**：后续内容的生成速度，常用 Token/s。

注意：用户感受到的「首字时间」还受排队、网络、服务端缓冲、额外推理计算影响，**不只由 Prefill 决定**。

## KV Cache：复用而不是重算

Decode 每生成一个 Token 都要用到历史所有 Token 的 Key/Value。KV Cache 把这些中间结果存下来，避免重复计算。

| 收益 | 代价 |
| --- | --- |
| 后续 Token 不必重算全部历史，生成更快 | 缓存占显存/内存，随上下文长度与输出长度增长 |
| 支持更长上下文下的可用速度 | 并发越高，缓存管理越关键；能否复用取决于推理服务实现 |

缓存容量与上下文长度的关系见 [上下文窗口](./s_ai_21-context_window)。

## 流式 ≠ 生成

「打字效果」是三层叠加的结果：

```text
模型逐步生成（自回归）
      ↓
服务端流式传输增量（SSE / WebSocket / 分块响应）
      ↓
前端接收、缓冲、更新界面
```

- 服务端可以边生成边发，也可以生成完再一次性返回。
- **SSE 只是传输方式**，不决定模型怎么生成。
- **一次传输的数据不等于一个 Token**：可能是多个 Token，也可能只是半个字符；前端还可能合并或人为调速。
- 页面逐字出现，不能反推模型内部就是「一次一个汉字」。

结论：**流式改善等待体验，本身不会让答案更准确**。传输细节见 [流式输出 Streaming](./s_ai_19-streaming)。

## 采样参数不是正确性开关

- **Token 概率 ≠ 事实正确率**：一个错误说法也可能又流畅又高概率，这就是幻觉的土壤（见 [模型幻觉](./s_ai_20-hallucination)）。
- **低 Temperature 不保证正确**，也不保证跨服务、跨版本完全复现；它只是让分布更集中。
- 没有适用于所有任务的默认值，要靠真实任务测试来定。

## 对工程的四条启示

1. **上下文是输入设计问题**：资料是否相关、是否冲突、超长时怎么截取或总结。
2. **流畅 ≠ 事实**：订单状态、金额、权限回源到业务系统，关键操作走确定性校验。
3. **性能要分阶段看**：首字慢查 Prefill / 输入长度 / 排队；出字后慢查 Decode / 并发 / 限流。
4. **流式要区分「文字」和「结果」**：页面提前出现「退款成功」，不代表业务操作已经成功——以业务系统返回为准。
