# 随机性、幻觉与能力边界：为什么调温度救不了可靠性

## 概念

接模型进业务，常被混为一谈的三件事：

| 问题 | 问的是 | 解决方向 |
| --- | --- | --- |
| 生成随机性 | 同样输入，为什么回答不一样 | 采样策略、任务评估 |
| 模型幻觉 | 回答为什么没有依据 | 资料、校验、兜底 |
| 能力边界 | 哪些事模型不能负责 | 分工与权限设计 |

一句话：**降随机性不等于消幻觉；接了工具也不等于能把决策和权限交给模型。**

随机性与幻觉的机制分别见 [Temperature 与采样策略](./s_ai_18-temperature)、[模型幻觉](./s_ai_20-hallucination)。本篇讲**它们和工程边界的关系**。

## 随机性不止来自采样

采样会让某一步选到不同 Token，后续上下文随之改变，回答就分叉了。但「换一次回答就不一样」还可能是：

- 模型版本变了、推理服务配置变了；
- 产品加了隐藏指令或联网搜索；
- 对话历史不同；
- 你比较的其实是两个不同产品。

所以做对比实验要**固定模型、完整输入、其他配置**，不能只让聊天框里的文字一样。

## 低温 ≠ 正确

温度只调整分布集中程度（公式见 [18](./s_ai_18-temperature)），它不改变模型知道什么。

关键结论：

> 低温度可能让模型**更稳定地重复同一个错误答案**。

稳定和正确是两回事。业务要的是一致性，就调低温度；但事实正确性得靠数据、校验和规则，不能靠"调到 0"。

## 三个能力边界

用户说「查订单 A1024 能不能退，能退就直接退」——这里有三个不同的问题：

| 边界 | 问题 | 模型能不能负责 |
| --- | --- | --- |
| **信息** | 有没有可信的订单状态、金额、适用规则 | 不能。要查业务系统 |
| **行动** | 能不能真的执行退款 | 不能。模型只提议，应用执行 |
| **决策** | 最终判断谁负责 | 不能。规则阈值、权限、风控归代码/人工 |

模型能做的是：理解诉求、提取参数、解释已核实的结果、在授权范围内建议下一步。

## 退款案例的正确分工

```text
查询订单 → 业务代码按规则算结论 → 模型把结论说成人话
```

| 组件 | 职责 |
| --- | --- |
| 订单服务 | 真实订单与状态 |
| 规则服务 | 按有效规则算审核条件 |
| 权限 / 风控 | 身份、授权、风险 |
| 大模型 | 理解请求、组织解释 |
| 退款接口 | 条件与授权都满足才执行 |
| 人工审核 | 需要人判断的情况 |

注意：「需要人工审核」≠「满足全部退款条件」≠「退款已执行」。三句话不能混。

## 只让模型润色，也会改错

业务代码算对了，模型改写时仍可能：改订单号/金额、把"需要审核"写成"已批准"、声称退款完成、加未经证实的时限。

所以：

- 关键信息**优先用确定性模板**输出；
- 允许润色就**校验输出**（订单号、金额、动作是否一致）；
- 模型挂了就用模板兜底，**但数据/规则失败时不许编结论**。

## 审一个「能自动退款」的 demo，看什么

| 检查项 | 不可靠的信号 |
| --- | --- |
| 主流程真的会跑吗 | 写完函数没调用（如 `main;`） |
| 边界输入 | 订单不存在时会不会直接空指针 |
| 失败路径 | 模型调用失败，能不能返回已算好的结论 |
| 输出校验 | 有没有核对模型改写后的订单号/金额/动作 |
| 规则完整性 | 是不是只判断了金额阈值 |
| 执行真实性 | 有没有真的调退款接口、读回执 |

一个能跑的 demo ≠ 一个能上线的系统。缺的通常是**异常、幂等、审计、人工兜底**。

## 失败时的三条降级

1. 业务结果已确定 → 返回**确定性模板**。
2. 关键数据/规则不可用 → **说明无法判断**，不要猜。
3. 操作结果不确定 → **回查业务状态**，不要直接说成功或失败。

降级内容必须与当前已确认的事实一致。

## 用评估代替参数猜测

- 业务事实对不对
- 信息不足时会不会停/问
- 工具参数对不对
- 权限与确认要求有没有守住
- 异常（工具失败、订单不存在）怎么处理
- 模型改写有没有改变权威结论
