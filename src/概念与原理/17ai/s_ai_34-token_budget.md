# Token 的工程账本：计数、上下文预算与成本

## 概念

Token 是模型处理文本的基本单位，切分结果由 **Tokenizer** 决定。机制本身见 [Token 与分词](./s_ai_8-tokenization)，这一篇只讲工程上的三个问题：

1. **数得准**：怎么统计一次请求的真实用量。
2. **算得清**：上下文预算怎么留。
3. **省得对**：Agent 的成本该从哪里优化。

## 切分为什么不规则

Tokenizer 不以人类语法为标准，它按自己的词表、预处理和算法编码。所以会出现：单词被拆开、标点与后文粘连、数字被切碎、改个空格结果就变。

| 常见误解 | 实际情况 |
| --- | --- |
| 「一个汉字 = 一个 Token」 | 取决于分词器，中文常见 0.5～1 字/Token，也有更碎的情况 |
| 「词表里有这个词，就一定会整体切」 | 预处理与合并规则也会影响；`2000 → 200 + 0` 只是特定分词器的结果 |
| 「BPE 就是从词表里找最长匹配」 | 不是。BPE 按训练得到的合并规则编码；最长匹配只是教学演示 |

结论：**要知道真实切分，就用目标模型对应的 Tokenizer 实测**，不要凭经验公式推算。

## 字符 ≠ 码点 ≠ 字节 ≠ Token

人眼看到一个 Emoji，可能由多个 Unicode 码点（含零宽连接符）组成；一个码点又可能占多个字节；最终对应几个 Token 由分词器决定。

```text
人眼字符数 ≠ Unicode 码点数 ≠ 字节数 ≠ Token 数
```

在字节级分词器里，单个 Token 的字节甚至不能独立解码成一个完整字符。可视化工具里的色块可以辅助理解，但别把它当成「一个色块 = 一个汉字」。

## 怎么数才准

| 方式 | 适用范围 | 局限 |
| --- | --- | --- |
| 可视化工具（如 OpenAI Tokenizer） | 快速感受切分差异 | 只代表所选编码；纯文本 ≠ 完整请求 |
| 本地库（如 tiktoken） | 提前估算、做预算 | 必须用与目标模型匹配的编码 |
| API 返回的 usage | 事后核对账单 | 事后才知道，且各服务口径不同 |

一次真实请求的输入，除了用户那句话，还包含：

- 系统 / 开发者指令
- 多轮对话消息与消息结构、特殊标记
- 工具定义、工具参数、工具返回结果
- RAG 检索内容
- 图片 / 文件等多模态输入

所以「把用户问题粘到 Tokenizer 里数一下」通常会**低估**实际用量。多模态和工具请求，优先看服务商的计数方法与文档。

## 上下文预算怎么算

假设窗口 8000 Token（输入输出共用，简化示例）：

| 内容 | 用量 |
| --- | ---: |
| 对话历史 | 5000 |
| 系统指令 + 工具定义 | 1000 |
| 剩余 | 2000 |
| 预留给输出 | 800 |
| **可给 RAG 的上限** | **≈1200** |

两个容易混淆的点：

- **上下文窗口 ≠ 最大输出长度**，是两个独立限制。
- 预留给输出的空间要按实际任务留，别把剩余空间全塞检索结果。

超出窗口时的常见策略与代价：

| 策略 | 代价 |
| --- | --- |
| 只保留最相关历史 | 可能丢前提条件 |
| 对早期对话做摘要 | 摘要会丢细节，且摘要本身也要花 Token |
| 减少 / 重排检索结果 | 可能漏掉关键条款 |
| 精简工具返回字段 | 可能误删状态、权限、风险信息 |
| 拆成多次调用 | 延迟上升，跨调用状态要自己维护 |

## 成本要按「任务」算，不是按「单次调用」

一个用户提问，在 Agent 里往往对应多次模型调用，每次都会**重新发送**一部分上下文：

```text
用户请求 → 调模型判断要查订单 → 工具返回 → 调模型分析 → 调模型写回复
                ↑ 历史与工具结果被重复带上
```

优化清单：

- 只送与当前任务相关的检索片段；
- 裁掉工具返回里的无关字段（但**不能省掉权限、状态、风险信息**）；
- 控制历史长度，用摘要而不是全量回放；
- 记录每次调用的输入/输出用量，**按任务汇总**看成本。

注意：提示词缓存（prompt caching）能降低计费，但**缓存命中不代表这些内容不占上下文窗口**。

## 速度不能线性外推

- 输入长 → 影响首 Token 延迟（Prefill 更久）。
- 输出长 → 影响总时长（Decode 更多步）。
- 但实际延迟还受并发、排队、网络、推理实现影响，**Token 减半不等于时间减半**。

推理链路见 [生成链路与推理性能](./s_ai_33-inference_pipeline)，窗口管理见 [上下文窗口](./s_ai_21-context_window)。

## Agent 开发的四条

1. **把上下文当预算**：不是「能不能塞进去」，而是「值不值得占用」。
2. **RAG 少而准**：多放文档会挤掉真正相关的内容，还可能截断。
3. **工具结果也要设计**：返回给模型前做裁剪与摘要，但保留必要字段。
4. **按任务看账**：调用次数 × 每次用量，才能定位真实成本。

## 面试常问

- 一个汉字大约几个 Token？这个估算能直接用吗？
- 为什么纯文本计数和 API 实际用量对不上？
- 上下文预算怎么留？窗口和最大输出是一回事吗？
- Agent 成本怎么降？提示词缓存会释放上下文窗口吗？
